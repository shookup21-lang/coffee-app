■ 버전(APP_BUILD) 규칙 — 중요
--------------------------------------------------------------------
- 형식: "수정한 실제 날짜-그날 순번" (예: 2026-09-18-01 → 같은 날 또
  수정하면 -02 → 다음 날이면 새 날짜-01)
- 과거에 날짜를 2026-08-20에 고정한 채 뒷번호만 올린 실수가 있었음.
  반드시 그날 실제 날짜로 바꿀 것.
- ※ 날짜는 반드시 "한국 시간" 기준. 작업 환경(컨테이너) 시계는 UTC라서
  한국이 자정을 넘겨도 date 명령은 전날로 나옴. 수정할 때마다
  `TZ=Asia/Seoul date +%F` 로 확인할 것. (2026-09-18 세션이 한국 시간
  자정을 넘겼는데 계속 09-18로 붙여 -15까지 간 실수가 있었음 → 9/19에
  "2026-09-19-01"로 바로잡음. 내용은 -15와 같고 버전 이름만 바뀜)
- 코드를 조금이라도 수정하면 반드시 바꿀 것. 안 바꾸면 기존 기기들이
  자동 업데이트를 감지하지 못함 (checkForUpdate가 문자열 비교함).
- 앱 하단(로그인/직원 홈/담당자 화면)에 "버전 ..."으로 표시됨.

■ 데이터 모델 (Firestore)
--------------------------------------------------------------------
- daily/{YYYY-MM-DD} 문서:
    - orders: { orderId: {team, name, drinkId, session, status, time,
      by, no, readyAt?} }
    - nextNo: 정수 (그날의 다음 수령 번호 카운터, 트랜잭션으로 증가)
  order.status: "pending"(대기) → "confirmed"(제조 중) → "ready"(완료)
  order.session: "am" | "ln"(점심) | "pm"
  order.no: 그날 리셋되는 고유 "수령 번호" (컵에 적어서 찾아가는 용도)
  order.by: 주문을 넣은 사람 이름 (대행 주문이면 name과 다름)
  order.pickedAt / pickedBy: -08~-14에서 쓰던 수령 기록. -15에서 수령
    추적 기능을 없애서 더 이상 쓰지도 읽지도 않음(예전 주문에 남아 있어도 무해).
  order.build: 주문을 만든 앱 버전 (2026-09-18-06부터 기록). 이 값이
    없는 새 주문 = 옛날 버전 앱으로 들어온 주문. 번호 중복 추적용.
- config/menu: {items:[{id,name,color,active,temp}]}  active:false=품절
  temp: "ice"|"hot" (-14부터). 없으면 menuTemp()가 이름 끝/앞에 HOT이
  붙은 것만 hot, 나머지(에이드·라떼 등)는 ice로 봄. 배열 순서 = 그룹 안
  표시 순서. 실제 메뉴는 아메리카노만 ICE/HOT 두 가지이고, 주문의 80~90%가
  ICE라서 어디서든 ICE 그룹을 먼저 보여줌(사용자 정보).
- config/teams: {items:[{id,name,color}]}  (팀 색상은 불러올 때 순서대로
  자동 배정. 팀 순번/로테이션 기능은 전부 제거됨)
- config/hours: {amStart,amEnd,amOn, lnStart,lnEnd,lnOn,
  pmStart,pmEnd,pmOn} — 세션별 on/off
- config/notice: {text, updatedAt} — 담당자 공지사항
- config/holidays: {days:{"YYYY-MM-DD":"사유(빈 문자열 가능)"}, weekendOff:
  true} — 평일 휴무일만 저장. 저장 시 지난 날짜·주말 날짜는 자동 정리.
  ※ 토·일은 코드에서 무조건 휴무(isWeekend, -13부터, 사용자 결정: "주말은
  무조건 쉬니까 버튼 필요 없음"). weekendOff:true는 아직 업데이트 안 된
  -10~-12 기기도 주말을 쉬게 하려고 저장만 해두는 값(새 코드는 안 읽음).
- 기기 로컬 저장(localStorage): ian_user(로그인 정보), ian_seen(확인한
  완료 알림 id 목록), ian_sound(담당자 알림 소리 on/off), ian_last(내가
  마지막으로 주문한 음료 id — "늘 마시던 걸로"), ian_guide(이용 안내를 한
  번 봤는지 — 처음 한 번만 펼침)

■ 핵심 로직 / 함수 (함수명으로 검색 — 줄 번호는 자주 바뀜)
--------------------------------------------------------------------
[주문 저장 — 가장 중요]
- commitNewOrder(fields) : 신규 주문 생성 전용. 트랜잭션으로 "번호 예약
  + 주문 저장"을 원자적으로 처리. 신규 주문은 반드시 이걸로.
  번호는 nextPickupNo(data) = max(nextNo, 오늘 이미 쓰인 최대 no) + 1.
- ※ 주문 몰림 대응 (-11): 모든 주문이 daily/{날짜} 한 문서에 모여서, 거의
  동시에 30명 이상이 누르면 트랜잭션끼리 충돌해 실패함(시뮬레이션: 예전
  버전은 30명 중 1명, 60명 중 5명 주문이 사라지고 화면엔 아무 안내 없음).
  그래서 commitNewOrder는 트랜잭션을 maxAttempts:3으로 시도 → 실패하면
  번호 없이 주문만 일반 merge 쓰기(충돌 없음)로 먼저 저장 → 번호는
  ensureMyNumber(본인 기기, 간격 두고 재시도)와 담당자 기기의
  repairPickupNos가 붙임. 번호가 없는 동안 pickNo()는 "…" 표시(예전의
  임시 순위 계산은 다른 사람 번호와 겹쳐 보여서 제거).
  txRun(fn): 기존 주문 수정 트랜잭션용 재시도 래퍼(최대 3회, 0.4~1.3초
  간격) — updateOrder/updateOrders/deletePendingOrder/repair에서 사용.
  주문 중엔 busyToast("주문 넣는 중이에요…"), 실패 시 "저장하지
  못했어요…" 안내. 전역 unhandledrejection도 같은 안내(안전망).
- stepOrder: 담당자가 '시작'을 누른 순간 직원이 음료를 바꿨으면

■ ⚠️ 다음 담당자(다른 Claude)가 할 일 / 작업 습관
--------------------------------------------------------------------
1. 위 "배포 상태"의 curl 명령으로 라이브 버전부터 확인.
2. 사용자가 가진 최신 index.html을 올려달라고 해서 작업 기준으로 삼을 것
   (작업 환경은 대화마다 초기화됨).
3. 코드 수정 시마다:
   - APP_BUILD를 "오늘 날짜-순번"으로 변경
   - <script type="module"> 블록을 추출해 `node --check`로 문법 검사
   - 동시성·경계값 로직은 Node.js로 간단히 시뮬레이션 후 전달
   - 디자인 변경은 가능하면 Playwright로 미리보기 캡처해서 확인
4. 사용자가 "업로드했다"고 해도 반영 안 된 경우가 과거 여러 번 있었음.
   raw 파일로 직접 재확인할 것.
5. 설명은 비개발자 눈높이로 쉽고 구체적으로 (버튼 이름·메뉴 위치 명시).
6. 주문을 수정하는 새 기능을 만들면 반드시 updateOrder를, 새 주문은
   commitNewOrder를 사용할 것. 전체 orders 맵 덮어쓰기 금지.
7. 작업을 전달할 때마다 handoff.txt도 갱신해서 index.html과 함께 전달 (요청이
   없어도 항상 — 사용자 요청 사항). 새 대화에서 이 문서만 보고 이어갈 수 있게.
